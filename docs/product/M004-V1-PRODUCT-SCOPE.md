## Product promise

A native, high-performance, persistent and agent-aware macOS terminal workspace. A developer can organize multiple projects, run shells and existing coding agents, switch between them without interrupting work, quit/reopen the GUI and reconnect, and jump directly to a terminal requiring attention. The core remains account-free and entirely OSS.

## Boundaries and architecture obligations

- Raw-only user-facing resting presentation during Blocks suspension, subject to #1493 acceptance. Preserve Block code/evidence; no Flow switch, composer requirement or alternate VT/grid/PTY. Defer Blocks and composer until after launch. This product decision is an explicit proposed scope amendment, not unilateral modification of accepted technical authority.
- Runtime owns live execution identity and PTY lifecycle; Rust client owns product presentation and navigation under ADR-015. CLI requests must use approved ownership boundaries, including GUI absence. No second Runtime, presentation registry or notification authority; do not make terminal processing wait on agents, notifications, persistence, licensing or cloud.
- Use existing Attention contracts and implementation where appropriate; define minimal terminal-scoped notifications without requiring a WorkItem/Attempt/AgentRun for ordinary CLI processes. Do not fabricate lifecycle/approval events or turn arbitrary terminal text into trusted agent state. Verify hook availability, provenance, replay/deduplication, permissions, cross-session isolation and secret-safe previews. Remote/untrusted output cannot acquire local control rights. No native approval execution in V1.
- Session persistence is not process resurrection. Keep durable metadata and bounded history asynchronous; keep explicit termination separate from UI close and distinguish detached from exited. Reconcile ADR-023, the sidebar and session inventory before production durability work.
- Templates are declarative local layout/cwd defaults, not workflow DAGs; automatic command execution requires explicit trusted configuration/consent. Worktree awareness is read-only context, not a worktree orchestration engine.
- CLI syntax, precise shortcut defaults, notification hook mechanisms, data schema, transport and component ownership details require refinement against existing ADRs/specs; do not treat illustrative chat commands as accepted syntax.
- OSS never depends on commercial code; the commercial repository consumes OSS through its pinned submodule.

## Required behavioral contracts before implementation

### Session inventory and workspace movement

The inventory/attach/detach/control contract is a prerequisite to workspace orchestration, not an output of durable persistence. Reuse the existing Runtime registry and controller/observer fences (ADR-017, SPEC-004/009); #929 is the UI consumer, not the missing Runtime API owner. Refine the existing Runtime owner and record the dependency before making the consumer Ready. Shell liveness, endpoint state, presentation attachment, controller ownership and termination are independent facts; unknown is never live. List operations must be bounded and must not attach or spawn.

**Verified current implementation gap (master at 89f7ca50):** `crates/seyal-runtime/src/runtime/local/session.rs::handle_list_executions` emits bounded `ExecutionListEntry` records with execution id, lifecycle, controller presence and attachment count; it truncates at `MAX_EXECUTION_LIST_ENTRIES` and does not encode WorkspaceId or a continuation. `crates/seyal-client/src/local/attach/execution_inventory.rs` filters to live execution ids, and `crates/seyal-client/src/app/unpresented_apply.rs::reconcile_live_unpresented` falls back to the implicit default workspace for unknown ids. Extend the existing SPEC-004 inventory path, not a new registry. Require authorized enumeration of all admitted workspaces and all visible executions with Runtime incarnation, authoritative WorkspaceId, ExecutionId, lifecycle and attachment/controller facts; bounded pages with explicit continuation/end or stale-snapshot outcome, no silent truncation. Fresh clients must not guess default workspace for an unknown execution. An ended/evicted execution is distinct from a live record and may be represented by bounded durable metadata after M004 persistence; absence or IPC failure is not proof of death. Qualify more than one page, mutation between pages, duplicate/missing entries, old clients, unknown ownership and exact adoption; preserve protocol version negotiation and existing limits.

One workspace has at most one presenting window and one execution has at most one bound terminal surface; selecting/opening/removing a sidebar row never changes execution ownership. Same-workspace moves preserve the execution, PTY, VT/history, and identity and fence old input before admitting the new route. Cross-workspace transfer is a deliberate user/authorized CLI operation, not an implicit effect of cwd change or navigation (ADR-028 explicitly requires a separate decision). Its required outcome is preservation of the live execution without respawn. Before implementation, accept a contract covering Runtime-authoritative WorkspaceId reassociation, permissions, identity/address/attention rebinding, layout/history association, exactly one controller/input route, concurrent close/terminate, rollback on partial failure and stale requests. Until accepted, cross-workspace transfer is blocked; never bypass the contract with duplicate bindings or a client-only reassignment. #1490 explicitly excludes live execution reassociation: complete its containment scope without enlarging #1494. Transfer is a separate launch-blocking refinement/production slice under #674, coordinated with #832 for persistent metadata, #680 for attention and SPEC-022 for addressing; it is not a prerequisite to merging a qualified sidebar slice. Establish whether the existing workspace-bound history/address contracts can preserve identity, and test interrupted commit, concurrent termination, stale attachment and notification before/after transfer. No migration of child process, PTY fd or canonical VT state. Closing a layout container detaches; explicit session close/terminate follows the accepted terminal-tab lifecycle and must make destructive intent clear.

### Bounded CLI and absent-GUI behavior

These are proposed product behavior requirements, not command syntax or a new IPC specification.

| Operation class | GUI absent | GUI present |
|---|---|---|
| List workspaces/executions, inspect status | Read authoritative local state, no implicit app launch | Same |
| Launch execution in existing workspace, explicitly terminate, detach own attachment | Operate through Runtime; a new execution may remain unpresented | Same; presentation adopts through its normal reducer |
| Interactive attach | Attach to the existing execution through the same Runtime protocol; allocate no second shell/PTY/VT. A controller conflict fails visibly; deliberate authorized transfer fences the old controller before input. Observer cannot write. CLI disconnect detaches, not terminates. | Same; no simultaneous uncontrolled writers |
| Create workspace | Runtime may create domain identity after validation; no invented headless pane tree | Same; GUI opens it through the existing presentation owner |
| Open/select workspace, split/move pane/tab, focus or apply layout template | Return a clear GUI-required outcome unless user explicitly requests opening GUI and awaiting its result; no silent queuing or competing layout state | Route through the sole Rust presentation reducer and confirm committed result |
| Notify | Accepted event retained independently of GUI | Same authority; UI/OS projection |

**Interactive attach is a separate launch gate from orchestration.** The CLI is a local display/input client of the existing Runtime, not a terminal emulator or transparent PTY-byte proxy. Render canonical bounded snapshots/damage into the host terminal using a negotiated, sanitized output representation; no replay of arbitrary child output or second writable VT/grid/history authority. A projection cache may exist only as disposable delivery state. Specify initial snapshot, scrollback/alternate-screen, cursor/style/Unicode fidelity, resync on loss, backpressure and host capability limits. Only the current controller may forward input/resize; negotiate the outer terminal geometry, fence resize and input on transfer, restore outer tty/mouse/alternate-screen modes on detach/error/signal and prevent nested-client loops. Fail visibly for unsupported host capabilities. Qualify real shell, SSH, Vim/tmux, resize, clipboard/escape safety, terminal disconnect, slow client, concurrent GUI takeover and no duplicate PTY; no new hot-path cost for non-CLI sessions. A host terminal's own rendering state is not a second Seyal execution authority. Refine the existing display/attachment contract before coding.

Use exact resource identifiers and typed request/results, documented machine-readable output/exit status, cancellation and bounded timeouts. No blind retry of mutation after unknown outcome; correlate requests to prevent duplicate execution. Distinguish read, create, input/control, notify and terminate capabilities; same UID alone does not prove a hook owns an execution. Do not expose arbitrary keystroke injection or destructive broadcast in V1. The exact transport, authorization and GUI activation protocol need an accepted refinement before production work; no terminal hot-path dependency.

### Durable restoration

Under #832/#687, require a versioned, consistent committed layout snapshot with stable Workspace/Window/Pane/TerminalTab identities and execution bindings; no intermediate split/reorder state becomes a recovered layout. Preserve proposed ADR-023's distinct single writers: Runtime P2/P3/P5 registry metadata/history manifests and immutable history packs, Rust presentation P4 layout/focus store, and the separate Agent Backend store. Atomicity is within each owning store, not a cross-store transaction. P4 references are hints reconciled against Runtime incarnation/identity/association on restore; record missing/stale bindings, never infer liveness from disk. Cross-workspace transfers and notification navigation use versioned reconciliation with explicit failure states rather than distributed transactions. Reconcile sidebar migration, persistence writer ownership and schema compatibility with ADR-023 before implementation. A crash during commit/migration must recover the last valid committed state or visibly report degraded recovery; reject unsupported schema, preserve recoverable data, and never silently overwrite it. On reopen, independently reconcile each persisted execution binding against Runtime identity, liveness and controller availability. Restore live bindings once, show detached/unavailable/ended entries and retained history honestly, leave unaffected panes usable, permit explicit retry/adoption or new shell. Never replay commands or silently substitute a new execution. Bounded asynchronous persistence and redaction remain mandatory. Prove GUI crash, Runtime loss, reboot, partial restore, corruption, migration, update/rollback and repeated reconnect.

### Notification lifecycle and trust

Reuse SPEC-028 / AttentionAuthority and SPEC-022 navigation; do not require managed agent runs for local shell hooks. Accept a terminal-scoped advisory ingress contract, including how it remains available without a GUI, before implementation. The existing agent backend must not become a prerequisite for terminal progress. **Verified current implementation gap (master at 89f7ca50):** `crates/seyal-agent-store/src/attention/ops.rs` exposes `mint_untrusted_terminal(summary, agent_run_id)` and run-scoped `list_for_run` / `protocol_view`; these are not an exact-execution, cross-workspace terminal inbox. Extend the existing Attention domain/store and projection contracts to support terminal targets, bounded enumeration and lifecycle operations by authorized execution/workspace, including executions without AgentRunId. No synthetic managed runs, separate notification database or dependency on managed agent authentication/dispatch/routing. Refine the minimal local authority hosting and startup/lifetime contract (including GUI absent), store ownership and bounded asynchronous ingress under #644/#680 before implementation; terminal use must work even if notification authority fails. Reuse existing store/typed domain where feasible; any ownership relocation requires separate accepted decision.

Provider qualification: Claude Code and Codex are required integrations with real documented supported versions; OpenCode must be qualified for available events with explicit version and capability coverage, not promised unsupported signals. Record per provider/event supported version, ingress mechanism, available event semantics, delivery/replay guarantees, known gaps and fixture plus real-run evidence. Generic CLI notifications remain available when hooks do not exist; absence of an event is never proof of completion or success. Provider hook setup is explicit opt-in; preview changes, preserve existing user hooks/configuration, scope to the exact local execution, support disable/uninstall and revoke credentials without deleting unrelated configuration. Do not capture prompts, credentials or full tool payloads by default. Record source identity and event correlation, exact ExecutionId and runtime incarnation, bounded sanitized preview, occurrence time and read/resolved/dismissed/expired facts. Approval-needed from an external tool is advisory spatial attention only (e.g. NeedsInput), never privileged ApprovalRequired, and cannot authorize an action.

Retain bounded unread/recent events across GUI quit/reopen through the existing authority; delivery failure must not lose canonical accepted attention. Coalesce duplicate/replayed events per source/target/correlation, rate-limit storms and report dropped/coalesced counts; fixed retention/count/size limits are required before implementation. Events and OS banners do not reorder workspaces. Acknowledge/read and dismiss are distinct from resolution or approval. Suppress redundant focused notifications; when GUI is absent, attempt native delivery where supported and permitted, otherwise surface retained unread attention on reconnect. OS denial must not break inbox delivery. Re-resolve exact target on click: navigate/reveal existing or offer authorized reattach if detached; if ended, removed, or unavailable, show retained details without spawning or focusing an unrelated terminal. Test stale incarnation, cross-workspace transfer, spoofed or unauthorized source, malformed payload and notification flood. No raw output may grant local control rights.

### Workspace templates and project context

A user can create a template from an existing layout (structure, names, cwd defaults only), name/edit/delete it, and explicitly instantiate it into a new workspace using GUI or bounded CLI. A template is versioned, validated and contains no execution IDs, captured secrets, shell history or commands copied from a live session. Launch validates paths and config, reports per-pane failures, preserves successfully created sessions and provides explicit retry or close; never silently retry processes or destroy unrelated executions. Reapplying requires explicit intent; it does not replace running layout automatically. If explicit launch commands are supported, require trusted local configuration and explicit consent; automatic command execution from untrusted repository files is forbidden. Read-only Git branch/worktree/cwd context is asynchronous, bounded and honest about stale/unknown metadata; no forced cd or automated worktree creation.
